# Changelog

## Unreleased

- CLI: the README (the one on npm) and the repo README say the CLI needs Node.js 20 or newer, how to check (`node --version`), and where to get it, and that `npx @userland.fun/cli` runs the CLI without a global install when `npm install -g` fails with a permission error. The repo README lists Node.js 20+ among an agent's inputs. The requirement itself is unchanged (`engines.node` has been `>=20`).
- CLI and schema: `userland validate` and the `apps publish` check refuse `"visibility": "private"` before anything is uploaded, with the API's message: `error=invalid_app_manifest`, `manifest_path=app.visibility`, "Private apps aren't available yet. Remove app.visibility or set it to public, and use sign-in with roles to limit who can see your app's pages and data." Userland never kept private apps private (anyone with the address could open them), so its API now refuses them too (dwrtz/userland#244). `schemas/resource-manifest-v0.schema.json` allows only `"public"`, and the plan check no longer reports a `private_apps` feature. `schemas/plans-v0.json` and `cli/tests/fixtures/plan-parity.json` drop `private_apps`, regenerated from the API's plan rules. Before, the CLI accepted `private` on Business and Business Plus and reported "Private apps: requires Business" on lower plans.
- CLI and schema: `userland validate` and the `apps publish` check refuse a `runtime.embed_origins` entry under `userland.link`, as they already refuse one under `userland.fun`, with the same message (`cannot be a Userland address: other apps and Userland sites can never show this app in a frame`). `schemas/resource-manifest-v0.schema.json` refuses both domains in any letter case. The Userland API will refuse `userland.link` entries too.
- CLI: `apps publish` prints `Published <address>` only when the new release is live. When the release is stored but not live (`activation_status` `pending_secrets`, `requires_migration`, or `failed`), the output starts with `Stored, not live: this release is not serving yet.`, then one `Why:` line for each reason, a line saying whether the previous release is still live or, on a first publish, that the address does not show the app yet, and `Next:` lines: for `pending_secrets`, one `apps secrets set` command for each missing secret (with the console's `?add-key=` link when the CLI knows the console) and the `apps publish <dir> --app <app-id>` command, keeping `--account`; otherwise, publish again with `--app` once the problem is fixed. A `Docs:` line links to the secrets, resource migrations, or troubleshooting guide. A live release whose address billing or the plan has turned off (`activation.billing_restricted`) prints a line saying visitors can't open it and `Next: userland accounts status`. The `key=value` lines are unchanged, and the exit code is still `0` whenever the release was stored, so a coding agent runs the next steps instead of publishing again without `--app`, which would create a second app. Before, every stored release printed `Published <address>`, even one that was not serving. `cli/tests/fixtures/activation-results.json` lists each result, what it means (whether the release is live, which release the address shows, whether the address is turned off, and which secrets are missing), and the exact output; Userland's other clients use the same meanings. The `userland-publish-operate` skill says to call an app live only when `activation_status=live`.
- Examples: the six public demos (`booking-app`, `invoice-generator`, `job-board`, `link-in-bio-app`, `mini-crm`, and `waitlist-app`) turn demo mode on at their addresses on `userland.link` as well as on `apps.userland.fun`: each `DEMO_HOSTS` list (and the invoice generator's `SHOWCASE_HOSTS`) has the demo's short address and its app-id address on both domains. The invoice generator's app-id address sends visitors to the demo address on the same domain, and the link-in-bio demo's owner view tells visitors to share the demo address on the domain they are using. Any other address on either domain, including your own copy's, still runs the normal signed-in app.
- CLI: `userland --help` ("Short addresses and domains") and the README say that `apps unpublish` also removes the short addresses and custom domains that a smaller plan or an unpaid invoice turned off, and keeps those short addresses for the account for 30 days, as `apps slugs remove` does, after the working ones. One that Userland support turned off still stays with the unpublished app until support turns it back on or releases it, and publishing the app again with its app id brings back none of the ones it removed. Before, both said a short address turned off by a smaller plan or an unpaid invoice stayed with an unpublished app and should be removed first. Userland's API changed this on 2026-10-04 for every CLI version; only the words change here.

## 0.11.0 - 2026-10-03

- CLI and schema: `userland validate` and the `apps publish` check accept `"provider": "stripe"` for a webhook, which Userland checks with Stripe's own `Stripe-Signature` header before the app sees the message. Like `generic_hmac` and `github`, it needs `secret`: the name of the app secret that holds the signing secret Stripe shows for the endpoint (`whsec_...`); without it the check reports `is required when provider is stripe`. It needs Starter or a higher plan (`webhooks.provider.stripe`), which the plan check reports as "Stripe webhooks: requires Starter." `schemas/resource-manifest-v0.schema.json` lists `stripe` with the signed providers, and `schemas/plans-v0.json` and `cli/tests/fixtures/plan-parity.json` have the new feature key, generated from the API's plan rules. Before, the CLI reported `stripe` as an invalid provider (`must be "none"`).
- Examples: `tiny-store` takes payment events straight from Stripe, with no relay. Its `checkout` webhook is `"provider": "stripe"`, and its job reads Stripe's own events, acting only on a Checkout Session whose `id`, `amount_total` and `currency` match the order: a `checkout.session.completed` or `checkout.session.async_payment_succeeded` event whose session is paid marks the order paid. A checkout paid by bank completes unpaid: the order becomes `payment_processing` (a new `status` value), which the hourly job doesn't cancel after 24 hours, until `checkout.session.async_payment_succeeded` marks it paid or `checkout.session.async_payment_failed` cancels it. A new `handled-events` collection remembers each Stripe event that paid an order, by its `id`, so the job ignores an event Stripe sends again later (Userland itself answers a repeat within 10 minutes once); the hourly job forgets events after 30 days, at most 500 a run. The README says how to add the webhook in Stripe's webhook settings, which three events to choose, and how to switch from Stripe's test mode to live mode, since the app checks one signing secret at a time. It still needs Business; `paid_features` lists `webhooks.provider.stripe` instead of `webhooks.provider.generic_hmac`. A copy that still uses a relay must point Stripe at the webhook's address instead and save Stripe's signing secret as `CHECKOUT_WEBHOOK_SECRET`: the job no longer reads the relay's body.

## 0.10.0 - 2026-10-03

- CLI: `userland accounts limits` prints `short_address_holds=held value=<n>` and `short_address_holds=max value=<n>` (`unlimited` when the plan has no limit): how many removed short addresses the account holds now and can hold at a time. A short address the account removes with `apps slugs remove`, or a working one removed by unpublishing its app, is kept for that account for 30 days, so only its own apps can add it again, unless the account already holds that many. It also prints a `usage_source=` line for usage that is not this period's counter: `usage_source=files.storage_bytes.max value=stored_files` means the `files.storage_bytes.max` usage is the size of every file stored now. Before, the CLI left both out.
- CLI: `apps domains add`, `list`, and `verify` print a custom domain's DNS records after its route and `verification=` lines, one `dns_record=` line each for the traffic record, the ownership TXT record, and any certificate validation records (each once), then `dns_ownership_status=`, a `dns_verification_error=` line for each record still missing, and `dns_last_refreshed_at=`. When `apps domains verify` answers `409 domain_pending_verification`, the error also prints the domain's `hostname` and `status` and the same `dns_` lines, so you can tell the owner which record to add. Before, the CLI printed only the error message, and no command showed the traffic record's target. `apps domains remove` prints none of these lines.
- CLI: API errors print `billing_url` (on `billing_restricted` and `downgrade_incompatible`: the account's Plan and billing page in the console) and `domain_url` (on `domain_pending_verification`: the console page with the domain's setup steps) under the error, as they already printed `upgrade_url` and `support_url`. `userland apps analytics` on a plan without App Analytics now prints `self_serve_upgrade`, `upgrade_url`, and `support_url` in its plain-text message too; before, they were only in `--json` output.
- CLI and schema: `userland validate` and the `apps publish` check accept only the content types the API accepts, in `files[].content_type` and in `resources.files.stores.*.allowed_content_types`: parameters separated by spaces or tabs, and quoted values of printable ASCII without `"`, `\`, or `,`. Values such as `text/plain;a="x,y"` passed the local check and then failed at publish with `400`. `schemas/resource-manifest-v0.schema.json` has the same rule, and its error now says "must be a MIME type such as text/html or image/png" instead of quoting the pattern.
- CLI: the README and `userland --help` say that an invite is only for someone who does not have an account in the app yet. For an email that already has one, setting a password on the link fails with `409 user_exists` and gives no new role. The README's error examples show the `upgrade_url` line that plan and quota refusals print, and the README explains short-address holds (including that one a smaller plan or an unpaid invoice turned off stays with an unpublished app) and the new domain lines.
- The `userland-publish-operate` skill tells agents to send the owner the console's `https://console.userland.fun/apps/<app-id>/settings?add-key=<NAME>` link for a secret whose value is theirs, instead of asking for it in chat, and to publish again with `--app` once the owner has saved it. Its description, and the one in `skills.catalog.json`, now include invites. The `ai-secret-tool`, `tiny-store`, and `webhook-automation` READMEs and `AGENT.md` files, and the `invoice-generator` README, give the same console link.
- Examples: the `mini-crm` and `waitlist-app` READMEs say "short address" instead of "slug".
- Examples: the READMEs and `AGENT.md` files of `booking-app`, `job-board`, `invoice-generator`, `mini-crm`, `link-in-bio-app`, `waitlist-app`, `blog-cms`, `tiny-store`, and `ai-secret-tool` invite people with `userland apps invites create <app-id> --email <email> --role <role>` (CLI 0.9.0 or later), which uses the key saved by `userland login`. Before, they made a new API key (which emails the owner) and called `POST /v0/apps/:app_id/admin-invites` with `curl`, then unset and revoked the key. `npm run validate:links` now refuses `admin-invites` and `api-keys create` in example READMEs and `AGENT.md` files.
- Examples: call the address you choose on apps.userland.fun a "short address", as the console and the Terms do, instead of a "named address".

## 0.9.0 - 2026-10-01

- CLI: add `userland apps secrets list <app-id> [--account <account-id>] [--json]`, which prints one tab-separated line for each secret that is set: its name, when it was first set (`created_at`), and when it was last set (`updated_at`). It never shows values: the CLI prints only the name and the two dates, in human output and in `--json` (`{ "app_id", "secrets": [{ "name", "created_at", "updated_at" }] }`), even if a response carried more. When no secrets are set, stdout is empty and stderr says so. It works with the key saved by `userland login`.
- CLI: add `userland apps secrets delete <app-id> <NAME> [--yes] [--account <account-id>]`. Server code that reads the secret stops getting it at once, and the value cannot be brought back. The command first checks that the name is set and stops with exit code `1` when it is not (the API answers a delete the same way either way, so before, a typo would have looked like a success). In a terminal it shows the secret, when it was last set, and the app's name, address, id, and account, and asks you to type the name or `y`; any other answer, or closed input, cancels and exits `1`. Without a terminal it needs `--yes` and otherwise stops with a usage error before sending anything. When an account is selected (`--account`, `USERLAND_ACCOUNT_ID`, or the saved account), it reads the app first, even with `--yes`, and deletes nothing in an app that belongs to a different account, as `apps unpublish` does. The output says to remove the name from `resources.secrets.required` too, or the next release you publish does not go live (`pending_secrets`) until the secret is set and you publish again.
- CLI: `apps secrets set` and `apps secrets delete` refuse secret names that start with `USERLAND_`, `CF_`, or `CLOUDFLARE_` before sending anything, as the API does. Before, `secrets set` sent them and the API refused them.
- CLI: add `userland apps invites create <app-id> --email <email> [--role <role>]... [--expires-in-days <1-30>] [--account <account-id>] [--json]` for inviting a person to sign in to an app that has sign-in (`POST /v0/apps/:app_id/admin-invites`). It prints only the invite link. `--role` repeats, one role for each flag (each role is sent once); with no `--role` the person gets no special role. `--expires-in-days` takes a whole number from `1` to `30` and is sent as `expires_in_seconds`; without it the link works for 7 days. `--json` prints the API response unchanged. It works with the key saved by `userland login` as well as `USERLAND_API_KEY`, so coding agents no longer need to make another API key (and the owner no longer gets a new-key email) to invite someone. When an account is selected (`--account`, `USERLAND_ACCOUNT_ID`, or the saved account), it reads the app first and creates no invite for an app that belongs to a different account, as `apps unpublish` does. A missing `--email`, a role with a comma in it, and a bad `--expires-in-days` are usage errors before anything is sent. `auth_disabled` and `invalid_role` errors link to https://docs.userland.fun/guides/auth.
- CLI: when `apps unpublish` or `apps secrets delete` stops because there is no terminal and no `--yes`, the command it suggests running keeps the `--account` you passed. Before, the suggestion dropped it, so running it skipped the check that the app belongs to that account.
- CLI: add `--cursor <cursor>` to `userland apps events`. When there are more events, the last line is `cursor=<cursor>`; running the same command again with `--cursor <cursor>` reads the next, older page.
- The `userland-publish-operate` skill lists the new commands, says to check which secrets are set with `apps secrets list`, to delete a secret only when the user asks and after checking the code no longer reads it, and to invite people with `apps invites create` instead of making a new API key, giving the link only to the user who asked.

## 0.8.1 - 2026-09-28

- Manifest: add the optional `runtime.embed_origins` list to `schemas/resource-manifest-v0.schema.json`. Apps on `*.apps.userland.fun` can no longer be shown in a frame on another site or another Userland app by default; to let your own website embed the app in an `<iframe>`, list that site, for example `"embed_origins": ["https://www.example.com", "https://*.example.com"]`. Each entry is `https://`, a domain name, and an optional port, optionally starting with `*.` to cover subdomains, with no path or trailing slash; at most 20 entries, and no Userland addresses (other apps, slugs, `userland.fun`, docs, the console, the API). It is available on every plan, belongs to the release (a rollback brings back that release's list), and does not affect custom domains. See https://docs.userland.fun/guides/embedding/.
- CLI: `userland validate` and the `apps publish` check apply the API's rules for `runtime.embed_origins` and use the API's messages, with one `error=invalid_runtime_manifest` block for each bad entry (the API stops at the first); a bad entry blocks the publish before anything is uploaded. Repeated entries and entries that start with `HTTPS://` in capital letters, which the API accepts and stores in lowercase without repeats, are `schema_strict` warnings. When the list is valid, human output adds an `embed_origins=` line with the sites as the API stores them, and `--json` output has a new `embed_origins` key (`[]` when none are listed, `null` when manifest errors prevent the check). The `userland-manifest-resources`, `userland-build-app`, `userland-publish-operate`, and `userland-debug-migrate` skills say when to list a site, that the app runs signed out inside the frame, and to keep the list in every release.

- CLI: when a rollback cannot update the app's server (`error=platform_deploy_failed`), the error now shows the `reason`, `status`, and `attempts` the API reports, the upload errors (`upload_error`) when the upload failed, and a line saying the rollback did not happen and the app is still on its current release. When the server did not start in time (which can happen when you roll back seconds after publishing a newer release) or the upload could not be taken just then (a 5xx or 429), that line says to run the same command again in a minute. When the upload was refused (another 4xx, such as server code that is too large) or could not be checked, running it again fails the same way, so the line says to send the output to support with `userland support open` instead. Before, the error showed only the message and the error code. Other commands print only these details for this error, with no advice, and other errors print as before.

## 0.8.0 - 2026-09-28

- CLI: add `userland apps unpublish <app-id> [--yes] [--account <account-id>] [--json]` for removing apps you no longer need, such as test or demo apps. It takes the app offline, removes its slugs and custom domains, and removes it from `apps list`; its release history is kept. In a terminal it shows the app's name, address, account, and whether it is a production app, and asks you to type the app id or `y`; any other answer cancels and exits `1`. Without a terminal it needs `--yes` and otherwise stops with a usage error before sending anything, asking you to check with the app's owner first. When an account is selected (`--account`, `USERLAND_ACCOUNT_ID`, or the saved account), it reads the app first, even with `--yes`, and does not unpublish an app that belongs to a different account. `--json` prints the API response (`app_id`, `status`, `deleted_at`). The app id is URL-encoded, and an empty id, `.`, or `..` is refused before anything is sent. The `userland-publish-operate` skill lists the command, mentions unpublishing in its description so agents asked to remove apps find it, and says to unpublish only apps the user named.
- CLI: a confirmation prompt (such as `auth api-keys revoke`) now treats closed input (Ctrl-D) as no instead of exiting without a word, and Ctrl-C exits with code `130`.
- CLI: publishing a folder no longer uploads dotfiles. Names that start with a dot (`.env`, `.env.local`, `.npmrc`, `.git/`, `.DS_Store`, and so on, at any depth) are left out with a `warning=dotfiles_skipped` line that lists them; `.well-known/` folders and dot-folders named by `runtime.static_root` or `runtime.server_entry` (such as `.output/public`) are still uploaded, and a `files` list in `manifest.userland.json` can still include a dotfile on purpose. A folder that holds a private key (`id_rsa`, `id_ed25519`, `.p12`, `.pfx`, or a `.pem` or `.key` file containing a private key) is not published and reports `error=private_key`.
- CLI: files listed in `manifest.userland.json` `files` must be regular files inside the app folder. A listed symlink, or a file inside a symlinked folder, is now an `error=symlink` instead of the `outside_app_directory` warning, so a copied template cannot publish a file from elsewhere on your computer. These checks, the release path rules, and the private key check also run with `--skip-local-validation`, before any file is read or sent.
- CLI: only the Userland manifest is left out of a folder publish. Before, every file named `manifest.json` at any depth was dropped, including web app manifests such as `public/manifest.json`. A top-level `manifest.json` is read as the Userland manifest (older name) only when there is no `manifest.userland.json` and it has `app`, `runtime`, `resources`, or `files`; otherwise it is uploaded as an ordinary file.
- CLI: an empty or missing value for `--app`, `--account`, or any other flag that takes a value is now a usage error. Before, `apps publish dir --app "$APP_ID"` with an unset variable created a new app. Empty `USERLAND_*` environment variables count as unset. `--value`, `--message`, `--subject`, and `--name` still accept text that starts with dashes, such as a PEM key; only a value that is exactly another option (`--value --account`) is refused.
- CLI: API keys are paired with their API. `USERLAND_API_KEY` goes to `USERLAND_API_BASE_URL` or `https://api.userland.fun`, never to a URL saved in the credentials file, and a saved key only goes to the API it was saved with (a different `USERLAND_API_BASE_URL` is an error). `login`, `signup`, and `auth save-key` no longer reuse a URL saved by an earlier login. API and console URLs must use `https://` (`http://` only for localhost), and a saved non-default API prints a `note=api_base_url` line.
- CLI: `login` checks the sign-in link from the API before printing or opening it: it must use `https://` and, for the default API or a set `USERLAND_CONSOLE_URL`, be on the Userland console. On Windows the browser is opened without `cmd.exe`.
- CLI: `apps secrets set` reads the value from stdin and `auth save-key` reads the key from stdin or a prompt that does not show the key. `--value` and `--api-key` still work but print a warning; the README and the `userland-publish-operate` skill now use the stdin forms.
- CLI: the credentials file is written through a temporary `0600` file and renamed into place. The CLI only sets the folder to `0700` when it creates it (or for `~/.userland`), and a malformed credentials file is reported without quoting its contents.
- CLI: app ids and secret names are URL-encoded in request paths for `apps publish --app`, `releases`, `rollback`, `secrets set`, and `events`, and `apps secrets set` checks the secret name locally (capital letters, numbers, and underscores, starting with a letter, up to 64 characters). An app id, slug, domain, API key id, or account id of `.` or `..` is refused before anything is sent: before, `apps slugs remove <app-id> ..` and `apps domains remove <app-id> ..` unpublished the whole app, and `apps publish dir --app .` created a new app.
- CLI: text from the API (event messages, app names, error messages, analytics labels) and file names in validation output are shown with control characters as visible escapes such as `\x1b`, so they cannot rewrite the terminal. `--json` output is unchanged.
- CLI: a new `login` revokes the API key saved by the previous login for the same API, and prints `revoked_previous_api_key_id=`. It revokes the key in the credentials file right before the new key is saved, so two logins running at once each revoke the key they replaced. `auth logout` without `--revoke` now says that the saved key still works.
- Harden the launch and capability examples after a security and abuse review:
  - Owner forms in every server example accept posts only from the app's own address, and refuse other sites, other `*.apps.userland.fun` apps, and `null` origins. `blog-cms` shows its editor only to signed-in admins.
  - Owner lists read every page instead of stopping at the first 100 or 500 rows (`booking-app`, `job-board`, `waitlist-app`, `invoice-generator`), with "Show more" or "Older" links where a page would get long.
  - Public forms have per-email and overall limits that also hold when many requests arrive at once (each save is counted again afterwards and undone when over the limit), a hidden spam trap, and a plain page when a limit or the plan's row limit is reached instead of an error. Owners can delete or clear out old entries to stay under the Free plan's rows.
  - `booking-app` blocks double booking with a unique hold for each half hour of a lesson, and confirming or reopening a request checks the calendar again. `invoice-generator` converts a quote to an invoice once and gives each document its own number. `booking-lite` answers `409 slot_unavailable` when two people book the same slot.
  - `tiny-store` marks an order paid only for a completed, paid checkout event whose amount and currency match the order, and refuses orders larger than the stock. `webhook-automation` stores each event once by its `external_id` and no longer has a public event list. `ai-secret-tool` never logs provider errors that could quote the key.
  - Server examples answer malformed or oversized bodies with `400`, `413` or `415` instead of `500`.
  - Demo modes cap how much one visitor, and the whole demo, can store, remove old rows as they go, and warn visitors not to type real details. Following each README's demo-removal steps still leaves a passing test suite.
- Example servers now answer `HEAD` like `GET`, with the same status and headers and no body. `waitlist-app`, `link-in-bio-app`, and the `blog-cms`, `booking-lite`, `server-notes`, `tiny-store`, and `webhook-automation` examples answered `HEAD` on their server pages with `404`. `booking-app`, `invoice-generator`, `job-board`, and `mini-crm` sent the page body with `HEAD`, and a signed-out `HEAD` on some owner pages got a `401` where `GET` redirects to sign-in. In `link-in-bio-app`, a `HEAD` on a link button no longer counts as a tap, and a `HEAD` on the demo's owner view gets the same redirect as `GET` without setting up a visitor copy of the sample data. Each example's tests check `HEAD` against `GET` with the new `expectHeadLikeGet` helper in `scripts/runtime-harness.ts`, and the `userland-runtime-code` skill now covers `HEAD`.

## 0.7.0 - 2026-09-27

- Add `userland validate <dir> [--plan <plan>] [--strict] [--json]` for offline checks against the published manifest schema, release file and path safety rules, and plan limits. Human output lists `manifest_path`, feature or limit key, value, allowed value, and required plan; `--json` returns a stable object. Exit codes: `0` valid, `1` errors, `2` plan limits exceeded. `--plan` accepts `free`, `starter`, `business`, and `business_plus`. Values no self-serve plan allows report `required_plan_key: "internal"` and a contact-support message with the https://docs.userland.fun/reference/limits/ link. Schema rules the API does not enforce (such as unknown `app` keys) are `schema_strict` warnings unless `--strict` is passed, and a top-level `$schema` key and the CLI keys `files`, `message` (the release message), and `provenance` are accepted (a wrong type for `$schema`, `message`, or `provenance`, which publishing ignores, is also `schema_strict`). The violated feature and limit keys, the highest `required_plan_key` per key, and the overall required plan match the API's `402` details; the CLI reports each job, collection, or store separately where the API combines them, `message` is the CLI's own wording, and `manifest_path` uses dotted paths.
- Add `schemas/plans-v0.json`, the public plan artifact (the self-serve plans Free, Starter, Business, and Business Plus, with features, manifest limits, and release limits) generated from the Userland API plan configuration, and ship both schema files in the CLI package.
- Run local validation before `apps publish` by default, checking plan limits against `--plan` or the account's own entitlements; add `--skip-local-validation`. Blocked publishes upload nothing. The API remains authoritative.
- Add `userland apps analytics <app-id> [--range 7d|30d|90d] [--account <account-id>] [--json]` and the `userland analytics` alias, with an upgrade message for accounts without App Analytics and an empty-state message.
- `userland accounts downgrade preview --to <plan>` now accepts only `free`, `starter`, `business`, and `business_plus` (and the older names `pro` and `team`); other values are a usage error.
- Print `self_serve_upgrade`, `upgrade_url`, and `support_url` from API `402` details, and link plan errors to https://docs.userland.fun/reference/limits/.
- Fix the `ai-secret-tool` example tag `secrets`, which is a reserved name the API rejects.
- Add six launch examples, each with a live demo and a page at `https://userland.fun/examples/<slug>/`: `booking-app`, `waitlist-app`, `mini-crm`, `invoice-generator`, `link-in-bio-app`, and `job-board`. All run on the Free plan. Each README covers installing the CLI, `userland login`, and getting an API key into `USERLAND_API_KEY` for the owner invite, and lists the steps to remove the demo mode; a "removing demo mode" test runs those steps on a copy of the app, and the demo-only tests live in each example's `tests/demo.test.ts`.
- Catalog entries and `example.json` now include `required_plan`, `paid_features`, and `launch_role` (plus `demo_url` and `page_url` for launch examples). `npm run validate:catalog` checks the plan fields against what `userland validate --strict` reports for each example.
- `schemas/resource-manifest-v0.schema.json` accepts the top-level keys the CLI reads (`$schema`, the release `message`, `files`, and `provenance`) and requires a secret for signed webhook providers on every delivery target.
